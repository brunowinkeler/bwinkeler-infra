# PostgreSQL provisioning

The shared PostgreSQL instance runs in `compose.prod.yaml` (service `postgres`,
network alias `bw-postgres`). It holds one **database per application** with two
roles each. The infrastructure owns databases, roles, and grants; applications
own their schema via migrations (ARCHITECTURE.md §11).

## Roles per application

| Role                    | Used by                     | Privileges                          |
| ----------------------- | --------------------------- | ----------------------------------- |
| `<service_id>_migrator` | one-shot migrate job        | owns the DB + `public`; runs DDL    |
| `<service_id>_runtime`  | the api container           | DML only (SELECT/INSERT/UPDATE/DELETE) |

The running backend never uses the migrator role. Neither role is a superuser.

## Provision a new application

Passwords are generated by you and passed via the environment (never on the
command line, never committed):

```sh
RUNTIME_PASSWORD="$(openssl rand -base64 24)" \
MIGRATOR_PASSWORD="$(openssl rand -base64 24)" \
  postgres/provision-app.sh lists
```

The script is idempotent: re-running it re-applies grants and rotates the
passwords to the supplied values. It verifies both logins over TCP at the end.

After provisioning:

1. store the passwords in the host secret files (mode `0600`):
   - `/etc/bwinkeler/apps/<service_id>/runtime.env` → `PGUSER=<service_id>_runtime`
   - `/etc/bwinkeler/apps/<service_id>/migration.env` → `PGUSER=<service_id>_migrator`
2. add `<service_id>_db` to `BACKUP_DATABASES` in `/etc/bwinkeler/backup.env`;
3. record the app in [`../docs/inventory.md`](../docs/inventory.md).

## Rotate a password

Re-run `provision-app.sh` with the new value(s), then update the matching host
secret file and restart the app container so it picks up the new credential.

## Decommission

Use `revoke-app.sh <service_id> --yes` only after a final verified backup and the
quarantine period (ARCHITECTURE.md §19.4). It is destructive.

## Notes

- Connections use `PGHOST=bw-postgres`, `PGPORT=5432` (no host port is published).
- `/docker-entrypoint-initdb.d` is intentionally not used — it runs only on first
  volume init and cannot provision an app added later (ARCHITECTURE.md §11.4).
- Superuser bootstrap comes from `/etc/bwinkeler/infra.env`
  (see [`../templates/infra.env.example`](../templates/infra.env.example)); the
  default superuser role is `bw_admin` (override with `PG_SUPERUSER`).
